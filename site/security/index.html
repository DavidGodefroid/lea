Security

lea’s security model

The boundary is the container and its proxy, not a prompt. Even a prompt-injected agent with every permission granted works inside these walls.

Each agent network is isolated from the host: the host has no address on it (Docker Engine 28.0 or later). lea refuses to start a container on a network that is not.

Egress

By default the allowlist holds the forges (GitHub, GitLab), the package registries (Go, npm, PyPI), the image registries and the model APIs. Each domain covers its subdomains; anything else is refused.

Only you change it, on the host: lea egress allow, lea egress deny, or LEA_EGRESS_ALLOW in ~/.config/lea/lea.conf. No agent, MCP tool or allowance reaches it.

A host of your network is reached only once listed in LEA_INTERNAL_HOSTS, and an internal name grants that name only: the proxy checks the TLS handshake’s server name.

The agents resolve no external name: lea starts their container with a resolver address that is never routed, so no lookup, from an agent or a container it starts, reaches your host’s resolver or the internet. The proxy resolves names for them. lea doctor fails on a container that resolves an external name.

What an agent can read

No API key or token is in the agent container’s environment or image. What lea gives the agents, though, they run as the owner of. lea doctor lists what is there, by path, never by value.

Inside the container

The entrypoint drops to your uid with no capabilities. The image has no sudo and no setuid file, so there is no way back to root.

lea’s seccomp profile is Docker’s default with a reviewed list of changes, each with its reason, checked in CI. It allows what the nested rootless Podman needs and keeps refusing the kernel keyring, bpf, perf_event_open and the kernel crypto sockets. On Linux the AppArmor profile lea applies too.

The proxy, the only container on both the agents’ networks and the egress network, runs with a read-only root, almost every capability dropped, and no service as root.

The kernel

Every lea container shares the host kernel, so the host’s patch level is part of the containment. lea doctor shows the kernel, Docker Engine, containerd and runc versions, and fails below the kernel minimum lea knows for your distribution.

LEA_RUNTIME=runsc (gVisor) or LEA_RUNTIME=kata (Kata Containers) puts a second kernel in the way, for the agent containers. Each has a cost and a few features it drops. A second kernel.

Signed releases

Each release is signed keyless with cosign by the release workflow: its checksums.txt and the lea and lea-proxy images, by digest. The installer, lea update and the background update verify the signature first, and stop when it is missing or bad.

Every signature is logged publicly (Rekor). The signature protects against a tampered asset or mirror; it does not replace trusting the GitHub account that publishes lea. Verify a release by hand.

What lea does not protect against

These limits are part of the design. Read them before you rely on lea.

A kernel bug

With the default runtime, one kernel bug reachable from the container is enough to escape it, whatever seccomp and AppArmor refuse. A second kernel narrows that surface; it does not remove it.

Files your host runs

The projects directory is writable, and an agent can write what your host tools would run: git hooks, .mcp.json, .claude/ settings, build scripts. lea reports changes to the first three when the last session closes; work in lea, not on the host, inside that directory.

Agents of one container

The agents of one lea share a uid. They can read each other’s environment and files, and the logins lea gives them. Use one projects directory per trust level.

What you allow

A domain you add to the allowlist, an internal host you list, an allowance you record: lea applies them as you wrote them. A domain that accepts uploads is a way out for data.
