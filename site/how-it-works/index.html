How it works

How lea works

One container per projects directory holds your agents. A proxy beside it is their only way out, and the deck is how you drive them.

The container

The container sees the projects directory (read/write) and a read-only allow-list of ~/.claude: hooks, skills, agents, commands and the top-level *.md files. settings.json and plugins are lea’s own copies, never written back.

Each projects directory gets its own container, internal network, agent history and login. Agents run under abduco, so closing the deck does not stop them.

The proxy

Every request of an agent goes through lea’s proxy. HTTPS reaches an allowlist of public domains: the forges, the package registries, the model APIs. Anything else is refused, with a first line that names the host and the command that allows it.

lea egress allow DOMAIN, on the host, adds a domain to the running proxy: no restart, and no agent can run it. Private and link-local addresses, public IP literals and DNS-over-HTTPS resolvers are refused whatever the list says.

The proxy also holds what the agents must use but not read: lea’s GitHub token, your providers’ API keys, and the SSH forwarders to the git endpoints you pinned.

The deck

One keyboard-first terminal: your agents in a column on the left, the selected agent’s terminal on the right. The mouse works too.

The deck’s main keys (? lists them all)
KeyAction
nstart a new agent
j kselect an agent
entertype into the selected agent
spacethe next agent that needs you
a d Aallow, deny, always allow a permission request
m tsend the agent a message, read its messages
sa shell in the container
qleave the deck; agents keep running

A red dot needs you, a spinner works, a green dot is done. A sound plays only when an agent needs you. The deck is optional: lea config deck off runs your own tool in the container instead, with the same confinement.

Teams of agents

Every agent has a role: lead, dev or reviewer. Only you change one. A lead starts devs and reviewers through lea’s MCP tools; any other agent asks a lead.

Agents message each other, report on their task (the deck and lea board show it) and lease the files they edit. An agent whose turn is over is woken when a message arrives.

A grant is a decision you record on the host and lea applies to every agent it covers: merge a pull request, close an issue, push the agent’s own branch. lea delivery on grants push, pull request and merge on the repositories of the projects directory.

Providers

Claude Code is the default provider. Codex is in the image, with its own login per projects directory, and runs any OpenAI-compatible endpoint that serves the Responses API: Ollama, vLLM, a server of your own.

An endpoint’s key file is mounted in the proxy only. Agents reach the endpoint at http://lea-proxy:4400/<name> and see neither the key nor the upstream.

The Locks

A Lock is a console that stands between your agents and a resource and alone holds its credentials. lea starts none of them: lox run does, for the projects directory, and decides their requests.

For each lock lox run runs (locksql, lockmq, lockfile, locklog), lea mounts that lock’s socket volume read-only on /run/<tool>, once Docker confirms it belongs to this projects directory. The agents reach the socket and nothing else: no credential, no profile, no audit log.

lockhttp works differently: its gate sits in the proxy’s network and every outbound request goes through it. Only the proxy joins the hub’s network; no agent reaches the hub.

Containers inside lea

lea never gets the Docker socket. docker and podman in lea reach a rootless Podman of the agent’s own, so tests and builds run as usual.

What an agent starts there is stopped once it has been idle 10 minutes, and removed when the agent ends. docker compose with its own networks does not work yet; docker run does.
